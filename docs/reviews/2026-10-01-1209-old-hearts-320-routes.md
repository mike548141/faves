# Old recipe hearts back beside the moved ones: every route, run

Evidence for roadmap `510/320`, 2026-10-02 NZDT (session `faves-4f`, branch
`510-320`). Nothing is built and nothing is deployed. This proposes a guard; it
does not ask for a ruling yet.

## The answer first

- 🔎 **No route reproduces the owner's state on two devices without an action
  he has already said he did not take, except one new candidate.** Every code
  path that could make a device that has synced before merge without a base was
  enumerated and run. None is reachable on his timeline.
- 💡 **The shape needs two things in one merge, not one.** It needs an *old
  list* (one still holding the four old ids and the three hearts removed days
  earlier) and a merge that *cannot tell an addition from a deletion*. Either
  alone is harmless. A lost base with no old list anywhere settles correctly. An
  old list against a good base **undoes** the move (PR #76's route); it never
  doubles it.
- 🤔 **New candidate, not yet put to the owner: receiving a shared favourites
  link.** "Add to favourites" on a shortlist shared before the move supplies both
  things with one tap, and reproduces his state exactly on both devices. It needs
  a link and a tap on a dialog headed "Add N favourites?".
- 🎯 **Proposed guard, in this order:** (C) a small sync log on the device, so
  the next sighting can be read instead of reconstructed; (A) no silent merge
  without a base on a device that has synced before; (B) optionally, a heart on a
  recipe someone moved follows it, whatever route brings it back. See *The
  guard*.

**Terms.** The *base* is the copy two devices last agreed on; sync compares
three copies (the base, this device, the server's) to tell a removal from an
addition. *Old* = the four `cook-at-home` hearts before the move. *Moved* = the
same four on their `u:` ids. *X* = the three hearts removed days before the
import.

## Why the routes in the brief are not it

Each was read and run; the evidence is the row named.

- **Schema and upgrade steps** (rows 8, 12). `UPGRADE_STEPS` is empty and
  `USER_SCHEMA` has been 1 at every commit (`git log -G'USER_SCHEMA = [0-9]'`),
  so the chain is the identity, the pre-upgrade snapshot has never been written,
  and the `110` pause has never fired. `STORE_SCHEMA.recipes` went to 2 in PR
  #60 (2026-10-01 01:07): a build older than that **pauses** on the server copy
  and merges nothing. `readBase` cannot return nothing for a stored object: the
  chain returns any object with a number `v` as it is.
- **Per-person cookbook and profiles** (rows 5, 5b, 9). Replace keeps every
  profile id (it starts from an empty registry, so no id is taken). A base for
  another id heals on the next cycle. The base is written only from a merge,
  whose ids are this device's and the server's. Not hearts, and not tested: a
  base written before `120` keys recipe hashes by recipe only, so the first
  recipe merge after `120` reads every recipe as new. No device held a recipe
  then.
- **The old-tab pause and resume** (row 12): never fired; when forced, the base
  is kept and the result is the move undone.
- **290/300/310** (row 13): `groupFavourites` and the "My recipe" label are
  display only. No key on an old or moved id is rewritten.
- **A service-worker update mid-session** (row 11): an old page and a new page
  over one storage. The old engine carries the move correctly; the old page's
  tap undoes it. Never both.
- **The backup Replace and the base**: the base is spared (`spare: true`) and
  the move then settles (row 0 and the existing `sync.test.js` test).
- **Anything that clears or rewrites the base**: only `enable`, `join` and
  `disable` remove it (the last committed test pins this). `writeBase` writes
  only after the server accepted the write; if it fails (storage full) the
  previous base stays. An old base still holds one of each pair, so it is safe.

**Why a stale read cannot do it either** (510/340's argument, which these runs
extend): a three-way merge keeps exactly one of a pair whenever each of its
three inputs holds exactly one. Every copy a device ever legitimately held, or
agreed, holds exactly one. So the union needs an input that holds both (an
additive write: Apply, a received shortlist), or a base that holds neither (no
base, or one for another person).

## What remains

1. 🤔 **The shortlist.** Did he, that evening, open a Faves link someone shared,
   or one he once sent himself, and tap "Add to favourites"? Any shortlist
   made before the import names the old ids, and one made before X went names
   X too.
2. **An old-list page plus a base-less merge in one cycle.** Old-list pages
   were live until PR #76. No code path to a base-less merge on his devices was
   found, but this is the route that a not-yet-found base fault would take.
3. **A copy of the app he does not count as one.** Each web address keeps its
   own storage, and the Worker accepts sync from two: `lets-eat.myspot.nz` and
   `faves.pages.dev` (`worker/wrangler.toml`). One browser that has opened both
   holds two copies. Only a copy that never finished a sync matters, and turning
   sync on there needs the code typed in, which he says he did not do.
4. **Untested:** a cross-tab race inside a Replace (another tab loading in the
   milliseconds between Replace's removals and its writes, where Chrome
   propagates storage between processes asynchronously). Run by reading, not by
   test. It deletes hearts rather than doubling them.

## The guard

Each is a proposal. None is built.

**C. A sync log on the device (recommended first).** Keep the last 20 cycles in
local storage: time, which page and build ran it, whether the base was present
and covered each person, and the keys each cycle added and removed. Show it in
Settings → Sync, with a copy button. It stays on the device and is never synced.
- *For:* the next sighting is read, not reconstructed. It would have answered
  320 in one look: which device, which page, which build, and whether that merge
  had a base. About half a day with tests.
- *Against:* a few KB of storage, and a list of heart keys on the device (the
  device already holds the hearts). It finds causes; it prevents nothing.

**A. No silent merge without a base on a device that has synced before.** When
`lastSyncedAt` is set and the base is missing, unreadable, or does not cover a
person both sides hold, and the merge would add to the server hearts it does not
hold, stop and ask: *keep what sync has*, or *add this device's extras
everywhere*. The same question covers a first join by a device that already
holds hearts (510/340's paper proposed that half).
- *For:* closes rows 1, 3 and 5 and every not-yet-found base fault. Client only;
  no Worker change, no extra network.
- *Against:* a question at pairing time and after a base loss, so more UI and
  words to get right. It does not touch rows 6 and 7: Apply and "Add to
  favourites" are additions the person asked for, and the merge is right to
  carry them.

**B. A heart on a recipe this person moved follows it (optional).** Each moved
recipe already records `movedFrom: "cook-at-home <dish>"` in the cookbook. Read
through one function, used wherever hearts, ratings and notes are read, merged
or imported, an entry on an old id that a recipe in this person's cookbook was
moved from becomes the moved entry, and the two collapse into one.
- *For:* makes "old beside moved" impossible by any route, including ones not
  found. No list of ids in the app's code: the map comes from the person's own
  cookbook, so a stranger's device is untouched.
- *Against:* it fixes the symptom, not the cause, and does nothing for X, which
  still come back on rows 1, 3, 5, 6 and 7. It is another key rewrite in the read
  path, the class this repo has been burnt by (one rule implemented twice). About
  a day with tests.

**Not proposed:** a one-line guard. None of these is one line.
