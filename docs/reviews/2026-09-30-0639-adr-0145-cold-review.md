## Headline

🔎 **The direction holds; one premise the owner ruled on did not.** ADR 0145
said personal recipes "will not fit" in local storage. They do: 1,651 bytes a
recipe (41,276 B across the 25 in Cook at Home), so about 5 MB holds more than a
thousand. Photos are what will not fit, and photos come later. The owner's
"move everything to IndexedDB" ruling was re-briefed on this and changed.

## Claims refuted or overstated

| # | Claim in 0145 | Finding |
|---|---|---|
| R1 | 164,716 B with menus, "about 13×" | That is one concatenated, reserialised stream. As a phone fetches them, 57 separately compressed files come to 204–208 KB (gzip); ratio about 16×. Brotli not measured |
| R2 | A `?h=` URL "is immutable, so it can be cached forever" | False on the server. `site/_headers:48` sets `max-age=0, must-revalidate` on `/data/*`, and header rules match paths, not query strings. A live probe returned the same ETag with and without `?h=` |
| R3 | Personal recipes "will not fit" | Unevidenced; they fit (above) |
| R4 | Home loads menus for search and the dish count | Also for the price chip (`app.js:77` → `price.js:58`), heart resolution (`app.js:1038` → `favourites.js:46-52`) and `picker.js:47` |
| R5 | Layer 3 is dish names and tags | Today's search also reads ingredients, attribution and order number (`search.js:180-215`). Names and tags: 38.9 KB gzip; with the rest, 48 KB. So home fetches about 51–60 KB, a saving of about 3×, not 13× |

Confirmed: `data.js:90`, `search.js:196`, `app.js:201`, `sw.js:229,264-281`,
the FX refresh bumping `DATA_VERSION`, `sync-merge.js:423` with no version check
in `sync.js`, `personal-data.js:539`, `FORMAT_VERSION = 1`, no IndexedDB or
`storage.persist` under `site/`, 12,274 B for one summary file.

## Defects

**Blockers**
- **B1** Per-partition server copies each expire 180 days after their own last
  write (`worker/sync-worker.js:87-99`). A store nobody edits (recipes) expires
  while favourites stay alive.
- **B2** No cross-partition atomicity. One conditional write today; N
  independent ones in the design, on a store with no true compare-and-swap
  (`sync-worker.js:271-285`). A refused write leaves the server with a state no
  device ever had, and a refused write is never retried (`sync.js:358`).

**Majors**
- **M1** "Switches over in one step" has no mechanism once `DATA_VERSION`
  retires: no install event, no Cache API transaction. `networkFirst` also
  stores every `/data/` response, including cache-busted rechecks
  (`sw.js:460`, `data.js:152-155`), with nothing to clean them up.
- **M2** An IndexedDB upgrade blocks while an old tab holds a connection, so the
  first build must close on `versionchange`. Seven modules repaint on the
  `storage` event, which IndexedDB does not fire.
- **M3** Every store reads synchronously (`settings.js:416`); IndexedDB is
  async. Either a wide refactor or a memory mirror with write-behind, which
  risks losing an allergen tap if the page is killed.
- **M4** Moving recipes to `u:` ids orphans their hearts, ratings, notes and
  ticks (`favourites.js:64`).
- **M5** Server cost: more reads per pull, an index key adds a write per push,
  and `MAX_BODY_BYTES` caps every copy at 256 KB.
- **M6** Splitting by store tells the server which kind of data changed, and
  when; unpadded ciphertext leaks sizes.

**Minors:** a deploy race can store new bytes under an old fingerprint (m1);
`storage.persist()` does not exempt a Safari browser tab from eviction, only a
Home Screen install (inferred, m2); the "move everything" list omitted
`faves.geo`, `faves.origin`, `faves.sync*`, `faves.personal` (m3); two version
numbers left unrelated (m4); `index.json` still needed by `recheckReferences`
and `check_fallback.py` (m5); freshness changes unnamed (m6); the refusal test
at `tests/personal-data.test.js:327` must flip (m7); the summary must run
through `load()` for dated fields (m8); "home region" needs a fallback when
location is declined (m9).

## Gaps

- **G1** Refusing newer data pauses sync for a household's un-updated phone;
  the base snapshot also needs the upgrade chain.
- **G2** "No code path lets an app update write to user storage" contradicts the
  upgrade chain itself, and the proposed test is vacuous (`sw.js` imports
  nothing).
- **G3** Phase 0 changes ADR 0127(b) without citing it. The authoring session
  confirmed 0127's "nothing is destroyed" holds in one direction only: an old
  device writes the server copy without the new store, and the newer device
  then reads that as a deletion.
- **G4** The two sync bugs lived only in the session log.
- **G5** The four-cost rule was asserted without today's costs measured
  correctly.
